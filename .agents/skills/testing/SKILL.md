# CoinTrail Backend Testing

Use this skill when adding, modifying, or verifying backend functionality under `cointrail-api/`.

Read `AGENTS.md`, the applicable implementation plan, and the existing tests before creating new tests.

## Core Principles

- Test behavior and business rules, not implementation details.
- Follow existing CoinTrail test patterns.
- Add tests appropriate to the change.
- Do not create tests merely to satisfy a checklist.
- Do not weaken, delete, or modify valid tests just to make the build pass.
- Investigate failures before changing production code or tests.
- Use PostgreSQL/Testcontainers when real database behavior matters.

## Before Writing Tests

Inspect tests for similar existing domains.

Useful reference areas include:

- account
- category
- transaction

Understand:

- test naming conventions
- Mockito usage
- MockMvc setup
- security test setup
- Testcontainers configuration
- integration-test structure
- helper methods and fixtures

Prefer consistency with the repository over generic examples.

# Service Unit Tests

Service tests should isolate service business logic where appropriate.

Mock dependencies such as repositories.

Test relevant behavior including:

- successful operations
- authenticated-user resolution
- ownership enforcement
- resource-not-found behavior
- duplicate detection
- validation involving other domains
- normalization such as trimming
- allowed and rejected state changes

Verify important repository interactions where they represent meaningful behavior.

Do not over-specify incidental interactions.

# Controller Tests

Use the project's existing controller test style.

Controller tests should focus on the HTTP/API boundary.

Test relevant behavior including:

- endpoint mapping
- HTTP method
- expected status code
- request JSON
- response JSON
- Jakarta validation
- malformed or invalid request values
- service invocation

Mock the service layer where appropriate.

For requests rejected during binding or validation, verify that the service is not called when relevant.

Do not reproduce service business-logic tests in controller tests.

# Repository Tests

Use repository tests when behavior depends on:

- PostgreSQL
- Flyway schema
- database constraints
- unique indexes
- foreign keys
- JPA mappings
- derived query behavior
- specifications or custom queries

Use the existing PostgreSQL Testcontainers pattern.

Repository tests should exercise the real database rather than mocking persistence.

Use `saveAndFlush()` when the test needs database constraints to execute immediately.

Examples of useful repository tests include:

- valid entity persists
- duplicate data is rejected by a database constraint
- invalid monetary values are rejected
- ownership-aware query returns only the correct user's data
- required relationships are enforced

Do not duplicate service behavior in repository tests.

# Integration Tests

Integration tests should validate important flows across real application layers.

Depending on existing project conventions, this may include:

HTTP request
→ Security/JWT
→ Controller
→ Service
→ Repository
→ PostgreSQL

Use integration tests for high-value scenarios rather than duplicating every unit-test case.

Prioritize flows such as:

- authenticated successful operation
- unauthenticated access rejection
- ownership isolation
- persistence of important domain behavior
- cross-domain relationships
- important business constraints

Inspect existing integration tests before adding new ones.

# Security Testing

For user-owned resources, include appropriate tests demonstrating that:

- the owning user can access the resource
- another user cannot access or modify the resource

Follow the application's established HTTP behavior for inaccessible resources.

Do not invent a different `403`/`404` strategy without checking existing behavior.

# Database Constraint Testing

If a Flyway migration introduces an important constraint, consider adding a repository test that proves the database actually enforces it.

Examples:

- unique constraint
- positive amount constraint
- required foreign key
- domain-specific uniqueness

Service validation and database constraint testing serve different purposes.

Where an invariant is protected at both layers, test each layer at the appropriate level.

# Test Data

Keep test data explicit and understandable.

Use unique values where database uniqueness matters, especially:

- email addresses
- user-owned names
- identifiers generated by fixtures

Do not make tests dependent on execution order.

Do not rely on data created by another test.

Seeded Flyway data may be used only when it is intentionally part of the application's database state.

# Running Tests

During implementation, run the narrowest relevant tests first.

Examples:

```bash
mvn -Dtest=BudgetServiceImplTest test
